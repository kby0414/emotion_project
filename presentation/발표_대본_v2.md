저희 팀명 ‘김정오’는 김범영, 정준영, 오석의 이름에서 한 글자씩 따서 만들었습니다. 조선의 지리학자 김정호를 떠올리게 해 기억하기 쉽다는 점도 고려했습니다.

발표 순서를 말씀드리겠습니다.

먼저 프로젝트의 목표와 팀 역할을 소개하고, 실제로 사용한 데이터의 범위와 EDA에서 확인한 품질 점검를 설명하겠습니다. 이어서 전처리 설계와 실행 결과를 보여 드리겠습니다.

다음으로 PyTorch GPU 학습 환경과 ResNet18, MobileNetV2, EfficientNet-B0의 구조와 선정 이유를 설명하고, 세 모델의 검증 성능과 현재 평가의 한계를 비교하겠습니다. 마지막은 모델 학습에 대한 웹캠 프로그램 구동에 대해서 보여드리고 마무리하겠습니다.

팀원별 역할입니다.

오석 팀원은 팀장과 OpenCV를 이용한 웹캠 실시간 프로그램 구현을 맡았습니다. 정준영 팀원은 프로젝트 주제 선정과 데이터셋 조사·수집, 전처리를 진행했습니다. 김범영 팀원은 전처리 보조 작업과 비교 모델 선정, PPT 제작과 발표를 맡았습니다.

## 슬라이드 4. 프로젝트 요약 — 약 50초

다음은 프로젝트 요약입니다.

전처리를 완료한 이미지는 총 27만 5,688장입니다. 이 가운데 방향 정보 때문에 옆으로 눕거나 거꾸로 보일 수 있었던 이미지 8만 3,308장의 방향을 바로잡았습니다.

원래 Training 데이터는 각 감정마다 4개 파트로 나뉘어 있었지만, 프로젝트 기간 안에 전처리와 세 모델 학습을 완료하기 위해 2개 파트만 사용했습니다. 따라서 이번 결과는 전체 Training 원천 데이터가 아니라 계획적으로 축소한 범위를 기준으로 합니다.

현재 제공된 Validation에서 Macro-F1이 가장 높은 모델은 EfficientNet-B0였고, 점수는 0.7357입니다. 다만 이 결과만으로 한 모델을 최종 모델로 고정하지 않았습니다. 전달받은 웹캠 프로그램은 EfficientNet, ResNet, MobileNet 가운데 하나를 선택해 실행할 수 있도록 설계되어 있어, 정확도와 실시간 처리 목적에 맞춰 모델을 바꿀 수 있습니다.

## 슬라이드 5. 전체 작업 과정 — 약 35초

전체 작업은 사용할 데이터 범위를 결정하고 원본 JPG 이미지와 JSON 라벨을 수집하는 단계에서 시작했습니다. 그다음 EDA를 통해 파일 수, 클래스 분포, 손상 여부, 이미지 방향과 데이터 분할 문제를 확인했습니다.

이 결과를 바탕으로 이미지와 라벨을 함께 전처리했고, PyTorch GPU 환경에서 세개의 모델을 학습했습니다. 모델 비교와 체크포인트 저장까지 완료한 상태입니다.

여기에 전달받은 Jetson 앱 소스 분석 내용을 연결했습니다. 웹캠 프레임을 입력받아 얼굴을 탐지하고, 얼굴별 ID를 추적한 뒤, 선택한 모델로 감정을 추론하고 확률을 화면에 표시하는 구조입니다.

## 슬라이드 6. 데이터 규모와 클래스 균형 — 약 35초

전처리에 성공한 데이터는 Training 22만 3,570장과 Validation 5만 2,118장으로, 총 27만 5,688장입니다.

분류 대상은 기쁨, 당황, 분노, 불안, 상처, 슬픔, 중립의 일곱 가지 감정입니다. 각 클래스의 비율은 약 14.13퍼센트에서 14.35퍼센트 사이로 차이가 매우 작았습니다. 가장 많은 클래스와 가장 적은 클래스의 차이도 620장이었습니다.

따라서 확보된 데이터만 놓고 보면 심한 클래스 불균형은 없었고, 별도의 오버샘플링이 꼭 필요한 상황은 아니라고 판단했습니다. 그러나 클래스 수가 균형적이라는 사실이 데이터 품질까지 보장하는 것은 아니므로, 다음과 같은 품질 문제를 추가로 점검했습니다.

## 슬라이드 7. 데이터 범위와 품질 점검 — 약 90초

EDA에서 확인한 핵심 문제는 네 가지입니다.

첫째, Training 원천 데이터는 각 감정마다 part 0부터 3까지 4개 파트로 나뉘어 있었습니다. 데이터 양이 매우 많고 프로젝트 기간은 제한되어 있어, 전처리와 세 모델 학습 시간을 줄이기 위해 약 절반만 사용하기로 했습니다.

하지만 라벨 JSON에는 전체 파트 범위가 남아 있었기 때문에 선택하지 않은 파트의 라벨 19만 3,589건에는 대응 JPG가 없습니다. 이 숫자는 전처리 코드의 실패나 예상하지 못한 누락이 아니라, 시간 제약에 따라 의도적으로 데이터 범위를 줄인 결과입니다.

둘째, 실제로 보유한 JPG 가운데 16장은 JPG 데이터 스트림이 손상되거나 잘려 있어 사용할 수 없었습니다.

셋째, 이 데이터에는 같은 사람이 촬영한 유사한 표정 이미지가 여러 장 있습니다. Training과 Validation에서 파일명 앞부분의 공통 식별자도 528개 발견됐습니다. 이 식별자가 같은 인물이나 같은 촬영 세션을 의미한다면, 모델이 감정 특징뿐 아니라 이미 학습한 사람의 얼굴 특징을 이용했을 가능성이 있습니다. 따라서 정확도가 높더라도 완전히 새로운 사람에게 같은 성능이 나온다고 단정할 수 없습니다.

넷째, 많은 이미지가 방향 문제가 있었습니다. 처음 전처리했을 때 일부 결과가 180도 돌아가 보인 것도 이 문제 때문이었습니다. 일반 뷰어에서는 정상으로 보여도 실제 픽셀은 회전된 상태일 수 있어, 전처리 과정에서 방향을 적용했습니다.

## 슬라이드 8. 전처리 설계 — 약 65초

전처리의 목표는 표정의 형태를 최대한 보존하면서 세 모델이 받을 입력 규격을 통일하는 것이었습니다.

먼저 이미지 크기는 224 곱하기 224로 선택했습니다. 이번에 사용한 세 모델의 torchvision 사전학습 가중치가 기본적으로 사용하는 입력 크기와 맞고, 27만 장이 넘는 데이터를 학습할 때 연산량과 GPU 메모리를 관리하기에도 적절했기 때문입니다.

이미지를 정사각형으로 강제로 늘리면 얼굴이 길어지거나 눌릴 수 있습니다. 그래서 원본 종횡비를 유지한 채 긴 변을 224에 맞춰 축소하고, 남는 부분만 검정색으로 채웠습니다.

또한 눈, 입, 눈썹의 형태와 명암에 집중하고 저장 공간을 줄이기 위해 1채널 흑백으로 변환했습니다. 다만 피부색이나 홍조처럼 색으로 나타나는 감정 단서가 사라질 수 있으므로, 향후 RGB 입력과의 비교 실험이 필요합니다.

저장 형식은 전처리 결과에 JPEG 재압축 손실이 추가되지 않도록 PNG를 선택했습니다.

## 슬라이드 9. 이미지 변환 전후 — 약 30초

왼쪽은 고해상도 RGB 원본이고, 오른쪽은 전처리한 224 곱하기 224 흑백 PNG입니다.

오른쪽 이미지가 정사각형이지만 얼굴 자체의 비율은 바뀌지 않았습니다. 원본의 가로세로 비율을 유지해 축소하고 남는 영역만 검정색으로 패딩했기 때문입니다. 또한 EXIF 방향을 먼저 적용했기 때문에, 저장 상태와 관계없이 모델에는 정상 방향의 픽셀이 입력됩니다.

## 슬라이드 10. 전처리 결과 — 약 55초

최종적으로 27만 5,688장의 이미지 전처리에 성공했고, 손상된 JPEG 16장은 제외했습니다. 제외 비율은 전체 보유 원본의 약 0.0058퍼센트로 매우 작습니다. 깨진 픽셀을 강제로 복원하면 오히려 학습 노이즈가 될 수 있어 제외하는 편이 합리적이라고 판단했습니다.

방향을 보정한 이미지는 8만 3,308장이었고, 이미지 크기 변경에 맞춰 JSON 라벨의 얼굴 박스 82만 7,064개도 같은 비율과 패딩 위치로 변환했습니다.

전체 처리 시간은 1시간 35분 35초였으며, 이미지 저장 용량은 약 513.40기가바이트에서 12.85기가바이트로 약 97.50퍼센트 감소했습니다.

컴퓨터가 재부팅되거나 작업이 중단되는 상황도 고려했습니다. 이미 완성된 PNG는 건너뛰고, 파일을 임시 이름으로 완성한 다음 최종 이름으로 교체하도록 했습니다. 처리 결과와 오류 원인은 `preprocessing_summary.json`에 기록했습니다.

## 슬라이드 11. PyTorch GPU 환경 — 약 55초

학습 환경은 Python 3.12.10 가상환경과 CUDA 12.6용 PyTorch로 구성했고, 실험에는 NVIDIA GeForce RTX 4060을 사용했습니다.

GPU 확인은 설치 화면만 보는 것으로 끝내지 않았습니다. 먼저 `nvidia-smi`로 GPU와 드라이버 인식을 확인했습니다. 여기서 표시되는 CUDA 버전은 드라이버가 지원하는 CUDA 호환 상한이므로, 실제 PyTorch 빌드가 사용하는 CUDA 런타임은 `torch.version.cuda`로 따로 확인했습니다. 이후 GPU에서 실제 행렬 곱셈까지 실행해 CUDA 커널이 정상 동작하는 것을 검증했습니다.

TensorFlow 대신 PyTorch를 선택한 이유는 성능이 부족해서가 아닙니다. torchvision에서 세 모델을 같은 API로 불러올 수 있고, 학습 반복문과 Macro-F1 계산, AMP, 체크포인트, 중단 재개를 한 코드에서 직접 관리하기 편했기 때문입니다.

## 슬라이드 12. 비교 모델 — 약 70초

비교 모델은 서로 다른 목적을 대표하도록 선정했습니다. 표의 파라미터 수는 7개 감정 분류기로 교체한 실제 학습 모델을 기준으로 한 근삿값입니다.

먼저 ResNet18은 잔차 연결을 사용하는 모델입니다. 여러 층을 통과한 결과에 이전 입력을 더해 기울기가 깊은 층까지 잘 전달되도록 돕습니다. 구조가 널리 검증됐고 학습이 안정적이어서 이번 프로젝트의 기준선으로 사용했습니다. 파라미터는 첫번째로 가장 많은 약 1,118만 개입니다.

MobileNetV2는 연산은 나눠서 가볍게 하고, 필요한 정보는 연결해서 전달하는 구조입니다. 그 결과 파라미터가 약 223만 개로 세 모델 중 가장 작기 때문에 웹캠이나 자원이 제한된 환경에서 빠른 추론을 기대할 수 있습니다. 다만 실제 실시간 속도는 웹캠 프로그램에서 FPS와 지연 시간을 측정해 확인해야 합니다.

EfficientNet-B0는 네트워크의 깊이, 너비, 입력 해상도를 균형 있게 조정하는 방법론을 바탕으로 합니다. MBConv와 SE 구조를 활용하며 파라미터는 두번째로 많은 약 402만 개입니다. 이번 Validation에서는 세 모델 중 가장 높은 성능을 보였습니다.

이렇게 안정적인 기준선, 경량성, 정확도와 효율의 균형을 대표하는 세 구조를 같은 데이터와 동일한 주요 학습 설정으로 비교했습니다.

## 슬라이드 13. 학습과 평가 설계 — 약 60초

세 모델에는 같은 Training과 Validation 데이터를 사용했습니다. 학습 데이터에는 좌우 반전과 작은 회전, 이동, 확대 정도의 약한 증강만 적용했습니다. 표정의 의미를 바꿀 수 있는 강한 변형은 피했습니다.

공통 설정은 최대 50 epoch, batch size 32, 초기 learning rate 0.0003, seed 42입니다. optimizer는 AdamW를 사용했습니다.

주 평가 지표는 Accuracy가 아니라 Validation Macro-F1로 정했습니다. Accuracy는 전체 정답률이지만, Macro-F1은 일곱 감정의 F1을 같은 비중으로 평균하기 때문에 각 감정을 고르게 분류하는지 확인하기 좋습니다.

Macro-F1이 세 번 연속 개선되지 않으면 조기 종료했고, 가장 높았던 시점의 가중치를 `best.pt`로 저장했습니다. 따라서 50 epoch는 반드시 모두 실행하는 횟수가 아니라 최대 학습 횟수입니다.

## 슬라이드 14. 세 모델의 검증 성능 — 약 55초

세 모델의 Validation 결과를 비교하면 EfficientNet-B0의 Accuracy는 0.7400, Macro-F1은 0.7357로 가장 높았습니다.

MobileNetV2는 Accuracy 0.7309, Macro-F1 0.7296이었고, ResNet18은 Accuracy 0.7275, Macro-F1 0.7253이었습니다. Macro-F1 기준으로 EfficientNet-B0와 MobileNetV2의 차이는 약 0.0062, ResNet18과의 차이는 약 0.0104로 크지 않습니다.

따라서 EfficientNet-B0가 현재 Validation에서 가장 좋은 결과를 냈다는 사실은 제시하되, 이를 단일 최종 모델 선정으로 해석하지 않았습니다. MobileNetV2는 훨씬 작은 모델이고 ResNet18은 안정적인 기준선이라는 별도의 가치가 있습니다. 전달받은 앱은 세 백본 중 하나를 선택해 실행하는 구조이므로, 실제 Jetson에서 모델별 속도를 같은 조건으로 측정해 비교해야 합니다.

## 슬라이드 15. 감정별 F1 — 약 50초

전체 평균만 보면 모델이 어떤 감정을 어려워하는지 알기 어렵기 때문에 클래스별 F1도 확인했습니다.

기쁨은 세 모델 모두 약 0.95, 중립은 약 0.83으로 비교적 잘 구분했습니다. 당황과 분노는 약 0.76에서 0.77, 슬픔은 약 0.71에서 0.72 수준이었습니다.

반면 불안은 약 0.56에서 0.57, 상처는 약 0.50에서 0.54로 세 모델 모두 낮았습니다. 특정 모델 하나만의 문제가 아니라 공통적으로 나타난 약점입니다. 불안과 상처의 표정 특징이 다른 부정 감정과 비슷하거나 라벨의 감정 경계가 모호했을 가능성이 있습니다.

그렇다면 사람은 불안한 표정과 상처받은 표정을 쉽게 구분할 수 있을까요? 다음 슬라이드에서 실제 Validation 이미지 두 장을 보겠습니다.

## 슬라이드 16. 불안과 상처 이미지 비교 — 약 45초

두 이미지는 같은 인물의 비슷한 촬영 환경에서 나온 실제 Validation 데이터입니다. 왼쪽 A는 상처, 오른쪽 B는 불안으로 라벨되어 있습니다. 눈과 입의 긴장 정도에 작은 차이는 있지만, 얼굴 표정만 보고 두 감정의 경계를 분명하게 나누기는 저희에게도 쉽지 않았습니다.

이 예시만으로 라벨이 잘못됐다고 단정할 수는 없습니다. 다만 감정 자체의 경계가 미묘하고 촬영 맥락을 함께 봐야 할 가능성이 있다는 점은 확인할 수 있습니다. 따라서 모델의 낮은 F1을 모델 구조의 문제만으로 해석하지 않고, 불안과 상처의 오분류 사례와 라벨 기준, 데이터 품질을 함께 분석해야 합니다.

## 슬라이드 17. 학습 결과 분석 예시 — 약 45초

이 슬라이드는 세 모델 가운데 EfficientNet-B0의 결과를 분석 예시로 보여 줍니다.

학습 곡선을 보면 학습 정확도는 계속 올라가지만 검증 성능은 약 0.74 부근에서 정체됩니다. 최고 성능은 15 epoch에서 나왔고, 이후 세 번 연속 Macro-F1이 개선되지 않아 18 epoch에서 조기 종료됐습니다. 이는 학습 실패가 아니라 최적점 이후의 불필요한 연산과 과적합 위험을 줄인 결과입니다.

혼동행렬에서도 상처와 불안 같은 감정이 다른 부정 감정과 섞이는 경향을 확인할 수 있습니다. 이 결과는 앞의 클래스별 F1에서 확인한 공통 약점과도 연결됩니다.

## 슬라이드 18. 세 모델 체크포인트와 팀 전달 파일 — 약 45초

학습 결과는 각 모델의 `best.pt`로 저장했습니다. 웹캠 프로그램을 담당하는 오석 팀원에게 ResNet18, MobileNetV2, EfficientNet-B0의 `best.pt` 세 개를 모두 전달했습니다.

`best.pt`에는 가중치뿐 아니라 모델 이름, 일곱 개 클래스의 순서, 입력 크기, 정규화 값과 최고 검증 지표도 함께 들어 있습니다.

## 슬라이드 19. 현재 결과의 한계 — 약 65초

현재 결과에는 네 가지 한계가 있습니다.

가장 중요한 부분은 한 사람의 유사 이미지가 많고, Training과 Validation에 동일 인물이나 촬영 세션일 가능성이 있는 식별자가 겹친다는 점입니다. 같은 사람의 이미지가 두 분할에 모두 들어갔다면 모델이 감정 특징과 함께 그 사람의 얼굴 특징을 기억해 정확도가 높게 측정됐을 수 있습니다. 따라서 현재 수치는 제공된 Validation 기준이며, 완전히 새로운 사람에게도 같은 성능을 보장한다고 말할 수는 없습니다. 향후에는 같은 인물이나 촬영 세션의 이미지를 한쪽 분할에만 배치하는 group split 검증이 필요합니다.

또한 Training은 시간 제약으로 감정별 4개 파트 중 2개만 사용했습니다. Training 라벨 19만 3,589건의 대응 JPG가 없는 이유도 이 계획된 범위 축소이므로, 전체 원천 데이터가 아니라 실제 사용한 두 파트 기준의 결과라고 명확히 보고해야 합니다.

현재는 흑백 입력만 실험했기 때문에 RGB 입력과의 직접 비교도 필요합니다.

마지막으로 학습 환경 기록상 MobileNetV2와 나머지 두 모델의 PyTorch 버전이 달랐습니다. 데이터와 주요 학습 설정은 같았지만, 더 엄밀한 재현 실험을 위해서는 동일한 패키지 버전이 기록된 환경에서 세 모델을 다시 학습하는 것이 좋습니다.

## 슬라이드 20. Jetson 실시간 감정 인식 구조 — 약 70초

이제 전달받은 OpenCV 기반 Jetson 프로그램의 처리 구조를 설명하겠습니다. 먼저 Linux의 V4L2 방식으로 카메라 장치를 찾고 웹캠 영상을 입력받습니다. 그다음 OpenCV의 Haar Cascade로 얼굴 영역을 빠르게 탐지합니다.

여러 사람이 동시에 보일 때는 얼굴 중심점이 얼마나 움직였는지와 얼굴 영역의 크기가 얼마나 변했는지를 함께 계산해 얼굴별 ID를 유지합니다. 이렇게 해야 한 사람의 감정 기록이 다른 사람에게 섞이는 문제를 줄일 수 있습니다.

탐지한 얼굴은 가로세로 비율이 찌그러지지 않도록 정사각형으로 맞춥니다. 그레이스케일 모드에서는 CLAHE라는 명암 대비 향상 기법을 적용해 1채널 224 곱하기 224 입력을 만들고, 컬러 모드에서는 OpenCV의 BGR 영상을 RGB로 바꾼 뒤 ImageNet 정규화를 적용합니다.

이 입력을 사용자가 선택한 모델에 넣어 GPU 또는 CPU에서 추론하고, 마지막에는 EMA로 감정 확률을 부드럽게 만든 뒤 바운딩 박스, 감정 이름, 확률과 장치 정보를 화면에 표시합니다. 문서에 나온 약 30 FPS는 목표 설정이며, 실제 Jetson에서 측정한 결과로 단정하지 않겠습니다.

## 슬라이드 21. 실시간 다중 얼굴 처리를 위한 최적화 — 약 65초

마지막으로 제한된 Jetson 자원에서 화면이 끊기지 않도록 적용한 최적화 방법입니다.

첫째, 카메라 영상은 계속 갱신하지만 AI 감정 추론은 두 프레임마다 한 번 실행합니다. 영상의 움직임은 부드럽게 보여 주면서 추론 계산량을 줄이려는 방식입니다.

둘째, 얼굴의 중심 이동과 크기 변화를 함께 이용해 사람별 ID와 감정 기록을 분리합니다. 셋째, 사용자가 모델이나 흑백·컬러 모드를 바꾸면 가중치를 백그라운드 스레드에서 불러와 화면이 멈추는 시간을 줄입니다. 예측 확률에는 0.35에서 0.40 정도의 EMA 계수를 적용해 감정 이름이 매 순간 튀는 현상을 완화합니다. 다중 얼굴 추론은 최대 0.15초로 제한해 프레임 드롭을 막도록 설계했습니다.

여기 표시한 320 곱하기 240, 30 FPS, EMA 계수와 0.15초는 전달받은 문서의 설정값입니다. 실제 장치 성능을 주장하려면 같은 카메라와 모델로 FPS와 지연 시간을 별도로 측정해야 합니다. 또한 MobileNetV2와 MobileNetV3-Small의 구조 차이를 해결한 뒤 가중치를 연결해야 합니다.

정리하면, 이번 프로젝트에서는 데이터의 손상과 방향 문제를 관리해 27만 5,688장을 동일한 입력 규격으로 만들었고, 서로 다른 장점을 가진 세 모델의 학습과 저장까지 완료했습니다. 여기에 Jetson용 OpenCV 프로그램의 얼굴 탐지, 다중 얼굴 추적, 모델 전환, 확률 안정화 구조를 연결해 전체 시스템의 흐름을 설명했습니다. 다음 검증 단계는 모델 구조를 일치시킨 뒤 실제 Jetson에서 FPS와 지연 시간을 측정하는 것입니다. 이상으로 발표를 마치겠습니다. 감사합니다.

## 발표 중 반드시 구분할 표현

- `193,589건`은 전처리 실패나 예상하지 못한 누락이 아니다. 시간 제약으로 Training 4개 파트 중 2개만 사용하면서 선택하지 않은 파트에 남은 라벨 수다.
- 실제 전처리에서 제외한 파일은 손상 JPEG `16장`이다.
- `0.7400 Accuracy`와 `0.7357 Macro-F1`은 현재 제공 Validation에서의 EfficientNet-B0 결과다. 새로운 사용자에게 같은 성능을 보장하는 수치가 아니다.
- EfficientNet-B0는 현재 검증 수치가 가장 높지만, 단일 최종 모델로 선정한 것이 아니다. 프로그램은 세 종류의 백본을 선택하는 구조다.
- 파라미터 수는 약 `ResNet18 11.18M`, `MobileNetV2 2.23M`, `EfficientNet-B0 4.02M`이다. 작은 파라미터 수가 실제 웹캠 속도를 자동으로 보장하지는 않으므로 FPS와 지연 시간을 별도로 측정한다.
- 50 epoch는 최대값이다. 세 모델이 18~21 epoch에서 종료된 이유는 Macro-F1 기준 조기 종료가 정상적으로 작동했기 때문이다.
- `last.pt`는 모델 학습 재개용이고, 전처리 재개는 이미 생성된 PNG를 건너뛰는 방식이다.
- 한 사람의 유사 이미지가 Training과 Validation 양쪽에 포함되면 정확도가 높게 측정될 수 있다. 현재 결과와 새로운 사람에 대한 일반화 성능을 구분해 말한다.
- 학습한 경량 모델은 `MobileNetV2`, 전달받은 앱 문서의 경량 모델은 `MobileNetV3-Small`이다. 구조가 달라 같은 가중치를 바로 사용할 수 없다.
- `320×240·30 FPS`, EMA 계수 `0.35~0.40`, 추론 제한 `0.15초`는 문서의 설정·목표값이며 실제 Jetson 실측값이 아니다.
